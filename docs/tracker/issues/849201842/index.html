[Security P0] Central SSO Session Fixation via Insecure Cookie Attribute on Login (/sso/login)

category Component: Security > Identity & Access Management > SSO
JD
pentest-team@company.com (Internal Red Team / Pentest) reported on October 09, 2026 14:00 UTC
reply more_vert

Executive Summary

During an authorized Red Team penetration test of the Identity & Central SSO platform, auditors identified a critical session fixation vulnerability in the primary authentication controller at /sso/login. The session identifier cookie (sso_session_id) was not regenerated upon successful credential verification, allowing an attacker to pre-set a session cookie on a victim's client and hijack the authenticated session immediately after login.

Affected Asset & Endpoint

  • API Endpoint: /sso/login
  • Code Location: //depot/identity/session_manager.py

Vulnerability Findings & Impacted Scope

  • sso_session_id session token reuse across auth boundary
  • Missing session.regenerate_id() invocation in login controller
  • Victim corporate credentials and IAM access permissions bound to pre-allocated session token

Reproduction Request

# Step 1: Pre-set attacker session cookie:
curl -c cookies.txt "https://auth.enterprise.internal/sso/login"

# Step 2: Victim logs in with valid credentials using the pre-set session cookie:
curl -b cookies.txt -X POST "https://auth.enterprise.internal/sso/login" \
  -d "username=victim_user&password=SecretPassword123"

# Step 3: Attacker accesses protected dashboard using original cookies.txt without logging in:
curl -b cookies.txt "https://auth.enterprise.internal/api/v1/auth/session/status"

Sample Response / Verification Payload

{
  "authenticated": true,
  "user_ldap": "victim_user",
  "roles": ["corp-engineer", "prod-deployer"],
  "session_id": "sso_pre_fixed_cookie_99812a"
}

Business & Security Impact

Critical corporate authentication bypass. Allowed arbitrary account takeover of corporate users on shared kiosks, lab workstations, or through subdomain cookie tossing attacks, compromising internal corporate network access.

Root Cause Analysis complete:

In //depot/identity/session_manager.py, the authenticate_user() handler was updating user state directly in the existing session record without calling session_store.regenerate_id().

Emergency hotfix PR #4701 created:
1. Invokes cryptographic session renewal (session_store.invalidate_and_regenerate()) upon every login.
2. Sends Set-Cookie: sso_session_id=...; HttpOnly; Secure; SameSite=Strict with new token.
3. Adds unit test suite //depot/identity:session_manager_test.
